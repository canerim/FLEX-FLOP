# CPU decoder audit, 2026-10-03

The released D12 synthesis decoder and both uniform exits of the e15
early-exit checkpoint exported to ONNX opset 17 and passed ONNX checker. On
the exact latent recovered from `kodim01_qp32.fufref2`, ORT CPU FP32 differs
from its respective PyTorch output by at most 4.8e-7. These checks validate
the graph conversion, not the routed, patchwise early-exit system.

The host is a dual-socket AMD EPYC 7443 system: 96 logical CPUs, AVX2, no
AVX-512. During every exploratory run the one-minute host load was roughly
90–130. Runs were `nice -n 19`, pinned to one CPU and one thread so active
training could continue. The recorded times vary widely and **cannot support
a speedup claim**. No oneDNN EP wheel is installed; all ORT results use the
standard CPU/MLAS provider. PyTorch reports oneDNN available, but its profile
shows that most convolutions do not actually take that path.

On Kodak 01 at QP32, the decoded source and released FP32 reconstruction have
Y/Cb/Cr PSNR 28.493/45.856/44.273 dB. Uniform e15 exit 0 gives
28.067/43.953/41.842 dB; uniform e15 deepest exit gives
28.485/45.850/44.226 dB. The latter is 0.007 dB below the released Y PSNR
on this single image. These are synthesis comparisons on the same decoded
latent, not routed bitstream results.

The initial all-Conv INT8 QDQ S8S8 trial used per-channel weights and reduced
range, calibrated on three Kodak/QP streams. On Kodak 01 QP32, Y PSNR falls
from 28.493 to 27.681 dB (−0.811 dB). Limiting INT8 to pointwise
convolutions at decoder positions 0–6 gives 28.245 dB (−0.248 dB).
These losses are too large for the current codec-quality target. The observed
single-thread INT8 latency was not better than FP32 ORT in the loaded-host
diagnostic. A larger, disjoint calibration and validation set, selective
quantization and an actual oneDNN EP are required before reconsidering INT8.

The instrumented PyTorch D12 pass recorded 72 convolutions: 58 calls through
`aten::_slow_conv2d_forward`, 14 through `aten::mkldnn_convolution`. The slow
convolutions, separate sigmoid/multiply passes, copies and additions are the
first optimization targets. Switching the model and latent to PyTorch
channels-last **did not** change that 58/14 split. Because almost all trunk
MACs are dense 1×1 channel mixing, a standalone AVX2 depthwise kernel is
unlikely to move end-to-end latency. Measure oneDNN pointwise primitives and
post-op fusion before writing custom C++; this machine cannot run AVX-512
intrinsics.

Next gated work: build an ORT wheel with DNNL EP in an isolated environment
once the training host has idle CPU capacity; compare DNNL FP32 to MLAS and
PyTorch under paired 1/2/4/8-thread, node-local runs; partition e15 into
stem, suffix, adapter and head ONNX graphs, retaining the decoder-side router
and tile scheduler; evaluate actual routed CPU bitstream-to-image latency and
PSNR. Profile that path before selecting a C++ fusion kernel. No training
process or GPU setting was changed by this CPU audit.
